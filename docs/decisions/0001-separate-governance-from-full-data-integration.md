# ADR-0001：治理平台不承担全量业务数据集成

- 状态：已被 ADR-0003 取代（产品定位转向临床试验数据质量管理平台）
- 日期：2026-09-18

## 背景

首期数据来自一个业务系统的少于 10 个 API。平台需要同时治理 API 资产与 API 返回的业务数据资产，并按设置的时间定时调用 API 完成探查和数据质量检测。

“调用 API”容易使平台边界扩张为全量同步、存储和加工系统，从而把数据治理、任务编排、ETL 和数据仓库职责混合在一起。

## 决策

DataStudio 首期只按检测计划调用业务 API，保存治理元数据、有限的探查证据、聚合检测结果和质量问题记录，不长期保存完整业务明细。

MySQL 是平台治理数据的事实存储，不作为业务系统全量数据仓库。API 资产和数据资产分别建模，并通过来源关系连接。

## 结果

### 正面影响

- 平台边界清晰，可优先交付目录、标准、责任制和质量闭环。
- 降低敏感业务数据复制、存储和泄露风险。
- 避免首期引入通用 ETL、海量存储和复杂数据加工能力。

### 代价与限制

- 质量检测受 API 能力、限流、分页和样本代表性约束。
- 平台不能直接支持依赖全量历史明细的质量规则。
- 后续如需全量同步，应接入独立的数据集成或湖仓能力，而不是隐式扩大本模块职责。

## 后续触发重新评估的条件

- 出现必须读取全量历史数据才能执行的治理规则。
- API 无法提供稳定、可分页或可增量读取的数据。
- 业务明确要求建设统一分析存储或跨系统数据加工能力。
